3막 · 보도 — 쓰고, 되짚어 확인하기

사실 대장만을 근거로 내 문체의 기사를 쓰고, 문장별로 검증하기

대상: 2막 · 취재를 마친 기자 — 2차 실습의 마지막 회차 (2시간)
도구: Claude Code + 내장 WebSearch
목표: 2막의 사실 대장을 근거로 뉴스가치에 따라 앵글을 정하고, 내 문체로 기사를 쓴 뒤 모든 문장을 근거 ID까지 되짚어 검증
핵심 원칙: 대장에 없는 것은 기사에 쓰지 않음. AI는 보조 기자이며 최종 판단과 책임은 사람 기자의 몫

1. 이 회차가 만드는 흐름

이번 회차의 입력은 원자료가 아니라 2막에서 만든 사실 대장. 자료를 다시 읽지 않음.

2_facts/fact_ledger.md   (2막 산출물: F1·F2·F3… 사실과 출처, 답한 질문 Q번호)
   │
   ▼ 0. 문체 학습(선택)   → 3_story/style_guide.md      (내 과거 기사에서 규칙 뽑기)
   │
   ▼ 1. 앵글 결정         → 3_story/angle.md            (뉴스가치로 무엇을 리드로 올릴지)
   │
   ▼ 2. 빈틈 보완(선택)   → 3_story/research_notes.md   (배경·맥락만. URL·확인일 표기)
   │
   ▼ 3. 기사 작성         → 3_story/article_v1.md       (내 문체, 문장마다 [F17])
   │
   ▼ 4. 팩트체크          → 3_story/factcheck.md        (문장별 판정, 독립 서브에이전트)
   │
   ▼ 5. 수정 반영         → 3_story/article_v2.md       (변경 요약 + 사람 확인 목록)

이 회차의 목적은 기사를 빨리 뽑는 것이 아니라 모든 문장이 어디서 왔는지 되짚히는 기사를 만들어 보는 것.

2. 핵심 아이디어 — 사실 대장이 유일한 근거

2막에서 만든 사실 대장의 모양. 각 사실에 F번호가 붙어 있고, 어느 질문에 답하는지와 출처가 함께 적혀 있음.

| id  | 사실(한 문장)                          | 답하는 질문 | 출처            | 검증 상태 |
|-----|----------------------------------------|------------|-----------------|-----------|
| F17 | A사가 2026-03-11 B사업 계약을 공시했다  | Q2         | DART 공시 4쪽   | 확인      |
| F18 | 해당 사업의 총 사업비는 3,400억원이다   | Q2         | 보도자료 2쪽    | 상충      |
| F19 | 인허가 심의는 2025-11 시작됐다          | Q1         | 의안 원문       | 미확인    |

이번 회차의 규칙은 하나. 대장에 없는 문장은 기사에 쓰지 않음.

이 규칙이 있으면 기사의 모든 문장이 "어느 자료의 어느 쪽에서 왔는지" 추적됨. 그래서 마지막 검증 단계가 형식이 아니라 실제로 작동하고, 근거 없는 문장(환각)이 걸러짐. 기자 입장에서는 "AI가 지어낸 것"과 "자료에 근거한 것"을 문장 단위로 구분하는 장치임.

2-1. [미확인]과 [상충]을 어떻게 다루나

대장에는 [확인]만 있는 게 아님. 이 셋을 다르게 다뤄야 함.

검증 상태기사에서
[확인]단정해서 쓸 수 있다. 문장 끝에 근거 ID를 단다.
[미확인]단정하지 않는다. 빼거나, 쓴다면 "확인되지 않았다"고 명시한다.
[상충]어느 한쪽을 고르지 않는다. 양쪽을 모두 제시하고 출처를 밝힌다. 종종 이것이 기사의 핵심이 된다.

그리고 답을 못 찾은 질문이 있다면 그 부분에서 기사는 침묵해야 함. 취재가 안 된 것을 문장으로 메우는 것이 가장 흔한 사고임.

3. 세 기능과 단계의 연결

단계 하는 일 체감하는 기능
0. 규칙·문체 뉴스룸 원칙과 기자 문체를 매번 자동 적용 CLAUDE.md
1. 앵글 결정 사실 대장을 뉴스가치로 평가해 무엇을 리드로 올릴지 정함 스킬(decide-angle)
2. 빈틈 보완 배경·맥락만 웹 검색으로 채움 (사실 추가 아님) 서브에이전트(WebSearch)
3. 기사 작성 사실 대장만 근거로 내 문체로 작성, 문장마다 근거 ID 스킬 + CLAUDE.md 문체
4. 검토(팩트체크) 문장별로 근거 ID를 되짚어 대조 검증 서브에이전트(독립 문맥·쓰기 권한 없음)

각 기능 요약:

  • CLAUDE.md: 프로젝트의 "근무 수칙 + 기자 문체". 매 작업마다 자동으로 읽혀 반복 설명이 불필요.
  • 서브에이전트: 추출·리서치·검증 담당을 각각 독립된 두뇌(별도 문맥)로 배치. 검증자가 작성자의 판단에 오염되지 않는 점이 팩트체크 신뢰의 핵심.
  • 스킬: 반복되는 표준 작업 절차(PDF 변환, 사실 대장 만들기, 기사 작성 규칙)를 정리해 두면 상황에 맞게 자동 적용.

4-3. 시작 전 준비 — 내 기사 넣기

수강생이 직접 준비할 것은 하나뿐. 본인이 쓴 과거 기사 3~5편을 style/my-articles/에 텍스트로 저장.

  • 이게 있어야 "AI가 쓴 것 같은 문장"이 아니라 본인 문체의 초고가 나옴.
  • 기사 형식이 서로 비슷한 것(스트레이트면 스트레이트끼리)으로 고르면 규칙이 더 또렷하게 추출됨.

사내 규정상 기사 원문 반출이 어려우면 문체 학습 단계를 건너뛰고 CLAUDE.md의 문체 규칙만 직접 작성해도 됨. 5-1의 "내 기사 문체" 절이 그 자리.

## 이번 회차(3막) 작업 순서

### 근거 규칙 (가장 중요)
- 이번 회차의 유일한 근거는 2_facts/fact_ledger.md 다. 대장에 없는 문장은 쓰지 않는다.
- 원문(2_sources/)은 대장의 출처를 되짚어 확인할 때만 본다. 새 사실을 캐러 가지 않는다.
- 검증 상태에 따라 다르게 쓴다.
  [확인] 단정 가능. 문장 끝에 근거 ID를 단다.
  [미확인] 단정 금지. 빼거나, 쓴다면 "확인되지 않았다"고 명시한다.
  [상충] 한쪽을 고르지 않는다. 양쪽을 모두 제시하고 출처를 밝힌다.
- 답을 못 찾은 질문이 있으면 그 부분에서 기사는 침묵한다. 문장으로 메우지 않는다.

### 순서 ("기사 써줘" 또는 /story 라고 하면)
- 0. 문체 학습(선택): style/my-articles/를 분석해 문체 규칙 정리. → 3_story/style_guide.md
- 1. 앵글 결정: decide-angle 스킬로 사실 대장을 뉴스가치로 평가해 리드와 각도를 정한다.
     왜 그 사실을 앞세우는지 근거를 함께 적는다. → 3_story/angle.md
     ★ 여기서 사람에게 앵글을 확인받고 다음으로 넘어간다.
- 2. 빈틈 보완(선택): researcher 서브에이전트로 배경·맥락을 웹에서 보완(URL·확인일 표기).
     ★ 새 '사실'을 추가하지 않는다. 독자가 이해하는 데 필요한 배경만 채운다.
     여기서 나온 항목은 R1, R2... 로 번호를 붙인다. → 3_story/research_notes.md
- 3. 기사 작성: write-article 스킬로 대장과 리서치 노트만 근거로 내 문체로 작성.
     모든 핵심 문장 끝에 근거 ID를 단다(예: [F17], [R2]). → 3_story/article_v1.md
- 4. 팩트체크: fact-checker 서브에이전트로 문장별 대조 검증. → 3_story/factcheck.md
- 5. 수정 반영: 팩트체크 지적을 반영하고 변경 요약을 붙인다.
     남은 [확인 필요]는 '사람이 직접 확인할 목록'으로 따로 뺀다. → 3_story/article_v2.md

각 단계 결과는 반드시 3_story/에 파일로 남긴다. 근거 없는 문장은 쓰지 않는다.
"N단계만", "3단계까지만" 같은 부분 실행도 지원한다.

## 내 기사 문체(요약)
- 리드는 한 문장, 핵심 수치를 앞세운다.
- 문장은 짧게, 피동·번역투를 피한다.
- 전문용어는 괄호로 짧게 풀어준다.
- 단정 대신 출처를 밝히는 화법("~에 따르면").
- 상세 문체는 style/my-articles/ 샘플을 우선한다.

## 뉴스가치 판단(기사 작성 시)
- 무엇을 리드로 올리고 무엇을 강조할지는 뉴스가치로 정한다.
- 기준: 새로움, 중요성, 사회적 파장, 유명성, 갈등, 그리고 근접성·이례성.
- 가장 가치 높은 사실을 앞세우되, 가치는 '선택과 강조'에만 쓰고 사실을 과장·왜곡하지 않는다.

## 금지
- 출처 없는 단정, 가짜 인용, 수치 왜곡(단위·기간 누락), 낚시성 제목.

5-2. 서브에이전트 (.claude/agents)

이번 회차에 새로 만드는 것은 둘. 2막의 extractor·verifier는 그대로 두되 이번 회차에서는 사용하지 않음.

researcher.md

---
name: researcher
description: 기사에 필요한 배경·맥락을 웹 검색으로 보완할 때 사용. 새 사실 추가용이 아니다.
tools: WebSearch, WebFetch, Read, Write
model: sonnet
---
너는 리서치 전문 기자다. 사실 대장은 이미 검증이 끝났다.
네 일은 독자가 기사를 이해하는 데 필요한 배경·맥락을 채우는 것이다.
- 제도의 정의, 사안의 연혁, 비교 대상(해외 사례·유사 사업), 용어 풀이가 대상이다.
- ★ 취재 대상에 관한 새로운 '사실'을 추가하지 않는다.
  그런 것을 발견하면 기사에 넣지 말고 "추가 취재 필요"로 따로 보고한다.
  검증을 거치지 않은 사실이 기사에 섞이는 것을 막기 위해서다.
- WebSearch로 신뢰할 1차 출처(정부·기관·학술)를 우선 찾고 WebFetch로 확인한다.
- 항목마다 R1, R2... 번호와 URL·확인 날짜를 단다. 확인 안 되면 [미확인]으로 남긴다.
- 사실 대장과 상충하는 내용을 발견하면 [상충]으로 표시해 보고한다. 임의로 판단하지 않는다.
결과를 3_story/research_notes.md 에 저장한다.

fact-checker.md

---
name: fact-checker
description: 기사 초안의 모든 문장을 사실 대장·리서치 노트·원문에 대조해 검증할 때 사용.
tools: Read, Grep, WebSearch, WebFetch
model: opus
---
너는 깐깐한 팩트체크 데스크다. 기사 초안의 검증 가능한 모든 문장을 하나씩 점검한다.

각 문장마다:
1. 문장 끝의 근거 ID를 확인한다. ID가 없는 문장은 그 자체로 [근거 없음]이다.
2. 그 ID를 2_facts/fact_ledger.md 또는 3_story/research_notes.md 에서 찾는다.
3. 대장의 사실과 기사 문장이 실제로 같은 말인지 본다.
   ★ ID가 붙어 있다고 통과시키지 마라. 흔한 사고는 "출처는 맞는데 의미가 부풀려진" 경우다.
4. 판정한다: [확인] / [출처 불일치] / [근거 없음] / [과장] / [미확인 사실 단정] / [상충 은폐]
   - [과장]: 대장에는 "계약을 공시했다"인데 기사에는 "수주에 성공했다"로 쓴 경우
   - [미확인 사실 단정]: 대장 상태가 [미확인]인데 기사에서 단정한 경우
   - [상충 은폐]: 대장 상태가 [상충]인데 기사에서 한쪽만 쓴 경우

인용은 원문과 글자 단위로, 수치는 단위·기간·반올림을 대조한다.
핵심 수치는 2_sources/의 원본까지 되짚어 확인한다.
문제 항목은 무엇이 틀렸는지와 수정안을 함께 제시한다.
결과는 '문장 / 근거 ID / 판정 / 근거 / 수정안' 표로 내고, 통과 못한 항목을 먼저 경고한다.
마지막에 근거 ID가 하나도 안 달린 문장의 수를 세어 보고한다.

fact-checker에는 일부러 Edit·Write 권한을 주지 않음. 검증자는 고치지 않고 지적만 하게 해 작성과 검증을 분리. 2막에서 추출자와 검증자를 갈라놓은 것과 같은 원리.

5-3. 스킬 (.claude/skills)

decide-angle/SKILL.md

기사 작성에서 AI가 가장 못하는 일이 앵글 판단. 그래서 이 단계를 따로 떼어 내고 사람이 확인한 뒤에 작성으로 넘어가게 설계함.

---
name: decide-angle
description: 사실 대장을 뉴스가치로 평가해 기사의 리드와 각도를 정할 때 사용한다.
---
# 앵글 결정 절차
입력은 2_facts/fact_ledger.md 와 1_plan/reporting_plan.md 다.

1. 대장의 [확인] 사실을 뉴스가치 기준으로 평가해 표로 만든다.
   - 새로움(이전에 알려지지 않은 사실인가, 시의성이 있는가)
   - 중요성(영향을 받는 사람·규모가 큰가)
   - 사회적 파장(정책·시장·여론에 미치는 후속 영향이 큰가)
   - 유명성(관련 인물·기관·기업이 저명한가)
   - 갈등(대립·쟁점·이해충돌이 있는가)
   - 근접성(우리 독자와 가까운가), 이례성(드물거나 의외인가)

| 사실 ID | 사실 | 강한 뉴스가치 | 왜 |
|---------|------|--------------|-----|

2. 앵글 후보를 2~3개 제시한다. 각 후보마다:
   - 리드로 올릴 사실 ID
   - 이 각도로 쓰면 기사가 무엇을 말하게 되는지 한 문장
   - 뒷받침할 사실 ID 목록
   - 이 각도의 약점(근거가 얇은 부분, 반론 여지)
3. ★ [상충] 사실이 있으면 그 자체를 앵글 후보로 반드시 포함한다.
   서로 다른 공개기록이 어긋난다는 것은 그 자체로 뉴스다.
4. ★ 답을 못 찾은 질문을 목록으로 보여준다. 이 각도로는 쓸 수 없는 영역이다.
5. 추천안과 이유를 밝히되, ★ 최종 선택은 사람에게 묻는다. 임의로 정하고 진행하지 않는다.
6. 3_story/angle.md 로 저장한다.

# 금지
- 뉴스가치를 높이려고 사실을 과장·왜곡하지 않는다.
  가치 판단은 '선택과 강조'에만 쓰고, 사실 자체는 그대로 둔다.

write-article/SKILL.md

---
name: write-article
description: 사실 대장과 리서치 노트만 근거로, 정해진 앵글에 따라 내 문체로 기사 초안을 쓸 때 사용한다.
---
# 기사 작성 절차
1. 근거는 2_facts/fact_ledger.md 와 3_story/research_notes.md 에 있는 것만 쓴다.
   앵글은 3_story/angle.md 에서 사람이 고른 것을 따른다. 임의로 바꾸지 않는다.
2. 구조: 리드(핵심 한 문장) → 핵심 사실 → 인용 → 배경 → 전망.
3. 문체는 CLAUDE.md와 3_story/style_guide.md 를 따른다.
4. ★ 모든 핵심 문장 끝에 근거 ID를 단다(예: [F17], [R2]).
   ID를 달 수 없는 문장은 쓰지 않는다. 이것이 이 회차의 핵심 규칙이다.
5. 검증 상태를 지킨다.
   [미확인] 사실은 단정하지 않는다. [상충] 사실은 양쪽을 모두 쓴다.
6. 해석·전망은 [추론]으로 표시해 사실과 구분한다.
7. 낚시성 제목을 달지 않는다.
8. 3_story/article_v1.md 로 저장한다(기본 800자, 지정 시 그 분량).

# 마지막에 스스로 점검할 것
- 근거 ID가 없는 문장이 남아 있는가? → 있으면 지우거나 ID를 찾아 단다.
- 대장에 없는 고유명사·수치·날짜가 들어갔는가? → 있으면 지운다.
- 답을 못 찾은 질문 영역을 슬쩍 메우지 않았는가?

6. 실행

작업 순서는 이미 CLAUDE.md에 정의돼 있음. 실행만 지시하면 Claude Code가 정해진 순서대로 서브에이전트와 스킬을 호출해 진행함.

전체 실행 (기본)

CLAUDE.md의 3막 순서를 0단계부터 끝까지 실행해줘.
1단계(앵글)에서는 후보를 보여주고 내가 고를 때까지 멈춰.
각 단계 산출물을 3_story/에 저장하고, 단계마다 무엇을 했는지 한 줄로 보고해.

앵글 결정에서 한 번 멈추게 하는 것이 중요. 여기가 기자의 판단이 들어가는 자리이며, 잘못된 각도로 끝까지 가면 전부 다시 써야 함.

부분·단계별 실행 (실습용)

기능을 하나씩 체감하려면 단계를 끊어 지시.

style/my-articles/ 를 분석해서 내 문체 규칙을 3_story/style_guide.md 로 정리해줘.
어떤 특징이 반복되는지 근거가 되는 문장도 같이 보여줘.

decide-angle 스킬로 앵글 후보를 뽑아줘. [상충] 사실과 답을 못 찾은 질문도 꼭 보여줘.

2번 앵글로 800자 기사를 써줘. 모든 핵심 문장에 근거 ID를 달아줘.

fact-checker 서브에이전트로 초고를 문장별로 검증해줘.
근거 ID가 안 달린 문장이 몇 개인지도 세어줘.

더 간단하게 — 커스텀 명령으로 만들기 (선택)

아래 파일을 만들어 두면 /story 한 번으로 실행 가능.

.claude/commands/story.md

CLAUDE.md의 "이번 회차(3막) 작업 순서"를 0단계부터 끝까지 실행한다.
1단계(앵글 결정)에서는 후보를 제시하고 사람이 고를 때까지 멈춘다.
각 단계 산출물을 3_story/에 저장하고, 단계마다 한 줄로 보고한다.
인자가 있으면 그 단계만 실행한다: $ARGUMENTS

이제 입력창에 /story(전체) 또는 /story 4단계만처럼 입력하면 됨.

권장 운영

처음에는 Shift+Tab으로 플랜 모드에 들어가 전체 계획을 먼저 확인한 뒤 실행할 것. 어떤 단계에서 어떤 서브에이전트·스킬이 작동하는지 한눈에 보여 교육용으로 특히 유용함.

6-5. 되짚기 시연 — 이 실습의 결론

기사가 나오면 마지막으로 아래를 실행. 2차 실습 세 회차가 무엇을 만들었는지 한 번에 드러남.

기사 세 번째 문단의 첫 문장을 골라서, 그 문장이 어디서 왔는지 끝까지 되짚어줘.
근거 ID → 사실 대장 → 어느 질문에 답하려던 것인지 → 원본 문서 몇 쪽까지.

한 문장이 [F17] → 사실 대장 → Q2 → DART 공시 4쪽까지 이어지는 것을 눈으로 확인하는 순간, 왜 1막에서 질문에 번호를 붙였고 2막에서 출처를 쪽수까지 적었는지가 설명 없이 이해됨. 강의의 마무리로 이만한 장면이 없음.

7. 운영·검증·윤리 팁

운영

  • 큰 단계 전에는 Shift+Tab으로 플랜 모드에 들어가 계획을 먼저 확인.
  • 권한은 처음엔 승인 모드로 두고, 파일 쓰기·검색·스크립트 실행 허용 범위를 직접 점검.

PDF 다루기

  • 변환본을 기준으로 작업하되, 핵심 수치·표·인용은 반드시 원본 PDF 페이지로 교차 확인.
  • 변환본이 비어 있으면 스캔본. OCR을 거쳐야 함.
  • 작은 텍스트 PDF는 Claude Code의 Read로 바로 읽을 수도 있으나, 표·수치 정확도와 대용량 처리를 위해 변환 권장.

검색

  • Claude Code 내장 WebSearch/WebFetch로 충분. 더 정밀한 검색이 필요하면 claude mcp add로 Brave·Tavily 같은 검색 MCP 연결.
  • WebFetch는 페이지를 요약해 주는 방식이므로, 정확한 인용과 수치는 항상 원문 기준으로 검증.

윤리 — 두 가지 강조

  • AI 보조로 작성했다는 사실을 밝힐 것.
  • 최종 인용과 수치는 사람 기자가 1차 출처로 다시 확인할 것. AI는 초안과 검증을 돕는 도구이며 출고 책임은 사람에게 있음.

8. 실습 체크리스트

  • [ ] style/my-articles/에 본인 과거 기사 3~5편을 넣었는가
  • [ ] CLAUDE.md에 3막 순서와 근거 규칙을 덧붙였는가

  • [ ] fact-checker에 Write 권한을 주지 않았는가
  • [ ] 앵글을 AI가 정하게 두지 않고 사람이 골랐는가
  • [ ] 기사의 모든 핵심 문장에 근거 ID가 달려 있는가
  • [ ] [미확인] 사실을 단정하지 않았는가
  • [ ] [상충] 사실의 양쪽을 모두 썼는가
  • [ ] 답을 못 찾은 질문 영역을 문장으로 메우지 않았는가
  • [ ] 팩트체크에서 통과 못한 항목을 사람이 확인했는가
  • [ ] 한 문장을 원본 문서 쪽수까지 되짚어 보았는가

9. 자주 막히는 곳

증상 해결
기사가 밋밋하고 남의 글 같음 style/my-articles/에 본인 기사를 더 넣고 0단계를 다시 실행. 형식이 비슷한 기사끼리 모을 것
대장에 없는 내용이 기사에 등장 researcher가 새 사실을 넣은 경우가 많음. "배경만, 새 사실 금지"를 다시 명시하고 팩트체크 재실행
근거 ID가 안 달린 문장이 있음 작성 프롬프트에 "ID 없는 문장 금지"를 다시 명시. fact-checker에 개수를 세게 하면 바로 드러남
ID는 맞는데 의미가 부풀려짐 가장 잦고 위험한 사고. 팩트체크 판정에 [과장]이 있는지 확인하고, 대장 원문과 문장을 나란히 비교
쓸 사실이 부족해 기사가 안 나옴 2막 취재가 얇았다는 신호. 억지로 채우지 말고 "추가 취재 필요" 목록으로 남길 것
서브에이전트가 호출되지 않음 /agents 로 등록 확인, 프롬프트에 에이전트 이름을 직접 지정
스킬이 적용되지 않음 폴더·파일명(.claude/skills/이름/SKILL.md) 확인, description을 상황 중심으로
검색이 빈약함 claude mcp add 로 Brave/Tavily MCP 추가
근거 없는 문장이 보임 작성 프롬프트에 "근거 id 없는 문장 금지"를 다시 명시, 팩트체크 재실행

10. 2시간 진행 순서

  • 0부(10분): 2차 실습 전체 되짚기 — 1막 질문, 2막 사실 대장, 그리고 오늘 할 일. 사실 대장을 화면에 띄워 놓고 시작합니다.
  • 1부(15분): 세팅 — CLAUDE.md에 3막 순서·근거 규칙 덧붙이기, 서브에이전트 2개·스킬 2개 저장, style/my-articles/에 본인 기사 넣기.
  • 2부(15분): 문체 학습 — 내 기사에서 규칙 뽑기. 뽑힌 규칙이 실제로 자기 문체와 맞는지 눈으로 확인하고 손봅니다.
  • 3부(25분): 앵글 결정 — 후보 2~3개를 받아 사람이 고릅니다. [상충] 사실과 답을 못 찾은 질문을 함께 확인합니다.
  • 4부(20분): 기사 작성 — 정해진 앵글로 초고. 문장마다 근거 ID.
  • 5부(25분): 팩트체크 — 문장별 판정. [과장]과 [근거 없음]을 찾아냅니다.
  • 6부(10분): 수정 반영과 사람 확인 목록 정리.
  • 7부(10분): 되짚기 시연(6-5)과 윤리 — AI 보조 사실 밝히기, 출고 책임은 사람.

강사 메모: 3부와 5부가 이 회차의 두 축입니다.

3부에서는 AI가 추천한 앵글을 일부러 한 번 반박해 보세요. "이 각도로 쓰면 무엇을 말하게 되나? 그걸 뒷받침할 사실이 대장에 몇 개나 있나?"를 물으면, 앵글이 취향이 아니라 근거의 문제라는 것이 드러납니다.

5부에서 가장 인상적인 장면은 [과장] 판정입니다. 대장에는 "계약 체결을 공시했다"인데 초고에는 "수주에 성공했다"로 적히는 일이 실제로 자주 일어납니다. 근거 ID는 멀쩡히 달려 있는데도 의미가 부풀려진 경우죠. 이걸 하나 잡아내면 "ID만 붙으면 안전하다"는 오해가 깨집니다. 미리 그런 문장을 하나 심어 두고 찾게 해도 좋습니다.

시간이 밀리면 2부(문체 학습)를 줄이세요. CLAUDE.md에 문체 규칙을 직접 적어 두는 것으로 대체할 수 있습니다.

바꿀 것은 다음뿐입니다.

  1. CLAUDE.md를 AGENTS.md로 이름만 바꿉니다(내용 그대로).

  2. 서브에이전트(researcher·fact-checker)를 .codex/agents/<이름>.toml 로 옮깁니다. 마크다운 프론트매터 대신 TOML 키(name·description·developer_instructions)를 씁니다. fact-checker에 쓰기 권한을 주지 않는 설정은 Codex에서도 유지해야 합니다(샌드박스 read-only).

# .codex/agents/fact-checker.toml
name = "fact-checker"
description = "..."            # 기존 description 그대로
developer_instructions = """
... 기존 지침 본문 그대로 ...
"""
  1. 스킬(decide-angle·write-article)은 SKILL.md 형식이 동일. 위치만 Codex 규칙(프로젝트 스킬 또는 ~/.agents/skills/)에 맞추고, 대화에서 $스킬이름으로 호출.
  2. 커스텀 명령 /story는 .claude/commands/story.md → ~/.codex/prompts/story.md로 이동. 호출은 /prompts:story. 하위 폴더는 인식되지 않으므로 최상위에 둘 것.

바뀌지 않는 것 — 사실 대장, style/my-articles/의 내 기사, 근거 ID 규칙, 폴더 구조, 프롬프트 문장. 이 실습은 별도 MCP 없이 Codex 내장 기능만으로 동작함.

Codex 실행 순서 (3막 전체)

  1. 같은 폴더에서 이어서 시작 
    cd newsroom_agent
codex
  2. 권한 — 샌드박스 workspace-write. 산출물을 3_story/에 써야 함.
  3. AGENTS.md에 3막 순서 덧붙이기 — 5-1절 내용을 그대로.
  4. 서브에이전트 2개 변환 — researcher · fact-checker를 TOML로.
  5. 문체 학습 
    /plan
style/my-articles/ 를 분석해서 내 문체 규칙을 3_story/style_guide.md 로 정리해줘.
어떤 특징이 반복되는지 근거가 되는 문장도 같이 보여줘.
  6. 앵글 결정 — 여기서 반드시 멈출 것 
    /plan
decide-angle 절차대로 앵글 후보를 2~3개 뽑아줘. [상충] 사실과 답을 못 찾은 질문도 꼭 보여줘.
내가 고르기 전까지 기사 작성으로 넘어가지 마.
  7. 기사 작성 — 사람이 고른 앵글 번호를 지정해 지시. 
    /exec
2번 앵글로 800자 기사를 써줘. 모든 핵심 문장에 근거 ID를 달아줘.
  8. 팩트체크 — 새 세션에서 실행하는 것을 권장(아래 주의점 참고). 
    fact-checker 에이전트로 3_story/article_v1.md 를 문장별로 검증해줘.
근거 ID가 안 달린 문장이 몇 개인지도 세어줘. 파일은 고치지 말고 지적만 해.
  9. 수정 반영과 확인 — /diff로 article_v2.md 변경 내용 점검.

Codex를 쓸 때 주의할 점

항목내용
fact-checker의 쓰기 권한 차단 이 회차에서 가장 중요함. Claude에서는 tools에 Write를 빼서 막았지만, Codex는 샌드박스가 세션 단위임. 두 가지로 보완: ① 팩트체크만 read-only 샌드박스의 별도 세션에서 실행. ② TOML 지침에 "파일을 수정하지 않는다. 지적과 수정안 제시만 한다"를 명시. ①이 확실함
앵글에서 멈추기 /plan과 /exec를 반드시 분리. /exec를 앵글 확정 전에 치면 임의의 각도로 기사가 끝까지 나감
웹검색이 약할 수 있음 researcher가 WebSearch에 의존함. 결과가 부실하면 검색 MCP(Tavily·Brave 등)를 config.toml에 추가. 다만 이 단계는 배경 보완용이므로 없어도 실습은 완결됨
근거 ID 누락 Codex는 지시를 문자 그대로 따르는 편이라, AGENTS.md에 "ID를 달 수 없는 문장은 쓰지 않는다"를 명시하면 효과가 큼
diff 확인 필수 /diff로 article_v2.md가 팩트체크 지적을 실제로 반영했는지 확인
