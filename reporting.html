2막 · 취재 — 모으고, 확인하기

공개기록에서 자료를 모아 개체를 뽑고 교차검증하기 — API · Playwright MCP · 독립 서브에이전트

대상: 1막 · 기획을 마친 기자 — 2차 실습의 둘째 회차 (3시간)
도구: Claude Code + 공개 API(DART·국회·뉴스) + Playwright MCP + Scrapling(선택)
목표: 1막의 질문 Q1·Q2·Q3…에 답할 자료를 모으고, 거기서 뽑은 개체를 다른 출처로 교차검증해 사실 대장 작성
핵심 원칙: 공개기록과 이용약관 안에서, 로그인 우회 없이. 수집과 대조는 자동, 판단과 게재는 사람

1. 이 회차의 구조 — 전반과 후반

2막은 2차 실습의 무게중심이라 3시간. 성격이 다른 두 작업이 이어짐.

1_plan/reporting_plan.md  (1막 산출물: 질문 Q1·Q2·Q3…)
   │
   ├───────────── 전반 · 모으기 (90분) ─────────────
   │
   ▼ 질문을 검색어·기관·기간으로 옮긴다
   │     Q2 "특별법 전후 수주가 늘었나" → DART 해당 법인 공시, 시행일 전후
   │
   ├─ DART 공시 · 국회 의안 · 뉴스        → API 스킬 (python 실행)
   ├─ 부처 보도자료 · 로그인/JS 페이지     → Playwright MCP
   └─ 안티봇·구조 변경 잦은 사이트         → Scrapling
   │
   ▼ 2_sources/  원문 + collection_log.md (출처·수집일·어느 Q에 답하는지)
   │
   ├───────────── 후반 · 확인하기 (90분) ────────────
   │
   ▼ 1. 개체 추출    인물·기관·금액·날짜  → 2_facts/entities.md   (extractor)
   │
   ▼ 2. 교차검증    다른 출처와 대조       → 2_facts/verified.md   (verifier · 독립 문맥)
   │
   ▼ 3. 사실 대장    질문 ↔ 사실 ↔ 출처    → 2_facts/fact_ledger.md
                                              F17 (Q2 · DART 공시 4쪽)  → 3막 입력

전반에서 배우는 것은 세 가지 수집 방식.

  • API(1순위): 구조화된 공개기록은 공식 OpenAPI로 받는 것이 가장 정확하고 합법적.
  • Playwright MCP(2순위): API가 없거나 로그인·자바스크립트 렌더링이 필요한 페이지는 브라우저를 조작해 수집.
  • Scrapling(3순위): 안티봇이 있거나 화면 구조가 자주 바뀌는 사이트는 적응형 스크래핑으로 처리.

후반에서 배우는 것은 검증자를 따로 두는 법. 뽑는 일과 확인하는 일을 서로 다른 서브에이전트에 맡겨, 확인하는 쪽이 뽑은 쪽의 판단에 오염되지 않게 함. 이 구조가 팩트체크 신뢰의 핵심.

이 방식은 국제 탐사보도의 표준 형태를 기자 한 사람 규모로 줄인 것. 대형 문서 조사에서도 "문서를 나눠 개체를 병렬 추출 → 기자들이 공개기록과 대조해 확인 → 관계를 지도로 병합"하는 흐름을 씀.

2. 소스별 최적 수집 방법

먼저 API를 찾고, 없을 때만 브라우저·스크래핑으로 내려갈 것.

소스 1순위 방법 도구 비고
기업 공시(DART) API opendart OpenAPI 무료 키, 공시목록·원본
국회 의안·회의록 API 열린국회정보 OpenAPI(open.assembly.go.kr) 무료 키
예산·재정 API 열린재정 OpenAPI(openfiscaldata.go.kr) 무료 키
법령·판례 API 국가법령정보 OpenAPI(open.law.go.kr) 판결서 전문은 열람 제한
뉴스 대조 API 네이버 뉴스 검색 API 1막 스크립트 재사용. 개체가 언론에 언제 등장했는지 확인
통계·공공데이터 API 공공데이터포털(data.go.kr) 선택 심화. API마다 활용신청 필요 — 8장 참고
부처 보도자료 브라우저/스크랩 Playwright MCP 또는 Scrapling 정책브리핑·부처 사이트
로그인·JS 페이지 브라우저 Playwright MCP 검색폼·페이지네이션
안티봇·잦은 개편 스크랩 Scrapling 적응형 선택자

판결서 인터넷열람처럼 본인확인·목적 제한이 있는 자료는 자동 수집하지 않음. 로그인 우회는 금지이며, 필요하면 사람이 직접 열람.

4. 준비

4-1. 1막 폴더에서 이어서 시작

1막에서 만든 폴더로 들어가 Claude Code 실행. 새로 만들지 않음.

cd newsroom_agent

# 가상환경 활성화 (터미널을 새로 열 때마다 필요)
.venv\Scripts\Activate.ps1          # PowerShell
# .venv\Scripts\activate.bat       # 명령 프롬프트(cmd) — PowerShell이 막힐 때
# source .venv/bin/activate         # macOS / Linux

claude

PDF 변환 패키지 추가. 1막과 같이 (.venv)가 켜진 상태에서 pip로 설치.

pip install pymupdf pymupdf4llm
pip freeze > requirements.txt

1막에 참석하지 못한 경우 — 배포된 1_plan.zip을 풀어 newsroom_agent/를 만든 뒤 시작. 1막의 CLAUDE.md·서브에이전트·스킬이 모두 포함돼 있음. 단 .venv는 압축에 들어 있지 않으므로 직접 생성 필요.

python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

4-2. API 키와 .env

각 포털에서 무료 키를 발급받아 .env에 추가(네이버 키는 1막에서 이미 입력). 키는 공유·커밋 금지이며 .gitignore에 .env를 넣을 것.

NAVER_CLIENT_ID=발급키          # 1막에서 이미 있음
NAVER_CLIENT_SECRET=발급키      # 1막에서 이미 있음
DART_API_KEY=발급키             # opendart.fss.or.kr
ASSEMBLY_API_KEY=발급키         # open.assembly.go.kr

두 곳 모두 무료·즉시 발급. 발급 페이지는 각각 opendart.fss.or.kr/mng/apiCertificateView.do, open.assembly.go.kr/portal/openapi/openApiActKeyPage.do.

키를 따옴표로 감싸도 무방. DART_API_KEY="abc123"처럼 써도 python-dotenv가 벗겨냄. 다만 따옴표 안에 공백이나 주석을 같이 넣지 말 것. 키가 안 먹는다며 헤매는 사고의 대부분이 여기서 발생함.

4-3. Playwright MCP 연결

브라우저 조작이 필요한 소스용으로 Microsoft Playwright MCP 연결. 구조화된 접근성 트리를 쓰므로 화면 캡처 없이 빠름.

claude mcp add playwright npx @playwright/mcp@latest

/mcp로 연결 확인. 처음 도구를 쓸 때 권한을 물으면 허용.

4-4. (선택) Scrapling — 안티봇·적응형 스크래핑

구조가 자주 바뀌거나 안티봇이 있는 사이트용. 라이브러리로 쓰거나 내장 MCP로 연결 가능.

pip install scrapling
scrapling install              # 브라우저·핑거프린트 의존성 설치 (.venv 활성화 상태에서)

MCP로 붙이려면(선택):

pip install "scrapling[mcp]"

# Windows
claude mcp add scrapling -- .venv\Scripts\scrapling mcp-server
# macOS / Linux
claude mcp add scrapling -- .venv/bin/scrapling mcp-server

Scrapling은 페이지에서 필요한 부분만 먼저 추출해 AI에 넘김. 토큰을 아끼고 선택자가 깨져도 스스로 위치를 다시 찾음. 시간이 부족하면 이 절은 시연만 하고 넘어가도 무방.

5. 전반 — 모으기

1막에서 만든 질문에 답할 자료를 수집. 여기서 가장 중요한 습관은 "이 자료는 어느 질문에 답하려고 받은 것인가"를 함께 적는 것. 그래야 후반과 3막에서 되짚을 수 있음.

5-1. CLAUDE.md에 2막 순서 덧붙이기

1막의 CLAUDE.md를 열어 "이번 회차(1막) 작업 순서" 절을 아래 내용으로 교체. 위쪽의 역할·원칙·폴더 규약·파이썬 실행 환경·질문 번호 규약은 그대로 유지.

## 이번 회차(2막) 작업 순서

### 전반 — 모으기 ("자료 수집해줘"라고 하면)
1. 1_plan/reporting_plan.md 를 읽고 질문 Q1..Qn 과 [확인 방법]을 파악한다.
2. 질문별로 어느 소스에서 무엇을 받을지 수집 목록을 먼저 만들어 보여주고, 승인받은 뒤 실행한다.
3. 소스별 최적 방법으로 자료를 받아 2_sources/ 에 저장한다.
   - DART·국회·뉴스: fetch-records 스킬 (공식 OpenAPI. .venv 활성화 후 python 으로 실행)
   - 보도자료·로그인/JS 페이지: Playwright MCP
   - 안티봇·잦은 개편: Scrapling
   - 판결서 인터넷열람 등 제한 자료: 자동 수집하지 않고 사람에게 넘긴다
4. 받은 파일마다 2_sources/collection_log.md 에 기록한다.
   반드시 [어느 Q에 답하는 자료인지]를 함께 적는다.
5. PDF는 pdf-to-md 스킬로 2_sources/sources_md/ 에 변환한다.
6. 소스별 수집 건수·실패·제한을 표로 보고한다.

### 후반 — 확인하기 ("개체 뽑아서 검증해줘"라고 하면)
7. extractor 서브에이전트 + entity-ledger 스킬로 개체 대장을 만든다. → 2_facts/entities.md
8. verifier 서브에이전트로 반복 등장·이상 신호 개체를 다른 출처와 교차검증한다. → 2_facts/verified.md
   verifier 에게는 extractor 의 판단이나 추측을 전달하지 않는다. 개체와 원문 위치만 넘긴다.
9. fact-ledger 스킬로 질문↔사실↔출처를 묶은 사실 대장을 만든다. → 2_facts/fact_ledger.md
   각 사실에 F1, F2, F3... 번호를 붙인다. 이 번호는 3막에서 기사 문장의 근거 ID가 된다.

각 단계 결과는 파일로 남기고, 단계마다 무엇을 했는지 한 줄로 보고한다.
한 단계만 실행하라고 하면 그 단계만 한다.

## 수집 윤리·법
- robots.txt와 이용약관을 지키고, 요청 간 간격을 둔다(과도한 트래픽 금지).
- 저작권 있는 본문은 수집·인용 범위를 지키고, 개인정보는 최소화한다.
- 제한된 자료의 접근을 우회하지 않는다. 못 받으면 실패로 기록하고 사람에게 알린다.

2번의 "먼저 보여주고 승인받는다"를 반드시 넣을 것. 수집은 되돌리기 번거롭고 API 호출 한도도 있음. 무엇을 얼마나 받을지 눈으로 확인한 뒤 실행하는 습관이 사고를 막음.

5-2. 서브에이전트 — .claude/agents/collector.md

---
name: collector
description: 취재 계획의 질문에 답할 자료를 공개기록·웹에서 수집해 2_sources/에 저장할 때 사용.
tools: Read, Write, Bash, WebSearch, WebFetch
---
너는 자료 수집 담당이다. 1_plan/reporting_plan.md 의 질문 Q1..Qn 에 답할 자료를 모은다.
- 수집 전에 "어느 질문에 어느 소스에서 무엇을 받을지" 목록을 먼저 보여주고 승인받는다.
- 구조화 공개기록(DART·국회·뉴스)은 fetch-records 스킬로 받는다.
  실행 전 .venv 활성화 여부를 확인하고, 활성화된 상태에서 python 으로 실행한다.
- 로그인·JS가 필요한 페이지는 Playwright MCP 도구로 검색·다운로드한다.
- 안티봇·구조 변경이 잦은 사이트는 Scrapling으로 받는다.
- 원문을 2_sources/에 저장하고, 각 파일의 출처(URL·수집일·소스명)와
  [어느 Q에 답하는 자료인지]를 2_sources/collection_log.md에 기록한다.
- robots.txt·이용약관을 지키고, 접근이 제한된 자료(로그인 우회 금지)는 건너뛰고 사람에게 알린다.

5-3-1. fetch_dart.py — 기업 공시

DART의 첫 관문은 회사 이름을 8자리 고유번호(corp_code)로 바꾸는 일. DART는 회사를 이름으로 다루지 않음. 전체 기업 목록 약 11만 건을 한 번 받아 캐시해 두고 사용.

"""DART 전자공시에서 취재 대상 기업의 공시 목록을 받는다."""
import io, os, pathlib, zipfile
import xml.etree.ElementTree as ET
import requests
from dotenv import load_dotenv

load_dotenv()

# ── 여기만 고쳐 쓰세요 ────────────────────────────────
COMPANIES = ["씨에스윈드", "SK오션플랜트", "유니슨", "두산에너빌리티"]
BGN, END = "20260101", "20260630"
# ────────────────────────────────────────────────────

KEY = os.environ["DART_API_KEY"]
META = pathlib.Path("2_sources") / "collection_log.md"
META.parent.mkdir(parents=True, exist_ok=True)
CACHE = pathlib.Path(".cache"); CACHE.mkdir(exist_ok=True)
CORP_XML = CACHE / "CORPCODE.xml"


def corp_index():
    """기업명 → corp_code 사전. 최초 1회만 내려받아 캐시한다."""
    if not CORP_XML.exists():
        print("기업 목록 다운로드 중... (최초 1회, 약 3.5MB)")
        r = requests.get("https://opendart.fss.or.kr/api/corpCode.xml",
                         params={"crtfc_key": KEY}, timeout=60)
        r.raise_for_status()
        with zipfile.ZipFile(io.BytesIO(r.content)) as z:
            CORP_XML.write_bytes(z.read(z.namelist()[0]))

    root = ET.fromstring(CORP_XML.read_text(encoding="utf-8"))
    idx = {}
    for e in root.findall("list"):
        name = (e.findtext("corp_name") or "").strip()
        # 상장사를 우선한다. 같은 이름의 비상장 법인이 섞여 있기 때문이다.
        if name and (name not in idx or (e.findtext("stock_code") or "").strip()):
            idx[name] = {"corp_code": e.findtext("corp_code"),
                         "stock_code": (e.findtext("stock_code") or "").strip()}
    return idx


index = corp_index()
print(f"기업 목록: {len(index):,}개\n")

rows = []
for name in COMPANIES:
    hit = index.get(name)
    if not hit:
        print(f"  [찾을 수 없음] {name}  ← 정식 법인명인지 확인하세요")
        continue

    res = requests.get("https://opendart.fss.or.kr/api/list.json", timeout=20, params={
        "crtfc_key": KEY, "corp_code": hit["corp_code"],
        "bgn_de": BGN, "end_de": END, "page_count": 100,
    }).json()

    if res.get("status") != "000":
        print(f"  [{name}] 오류: {res.get('message')}")
        continue

    items = res.get("list", [])
    total = res.get("total_count", len(items))
    warn = "  ← 100건에서 잘림. 기간을 좁히세요" if total > 100 else ""
    print(f"  {name} ({hit['stock_code'] or '비상장'}): {len(items)}건 / 전체 {total}건{warn}")
    for it in items:
        rows.append({
            "corp": it.get("corp_name"),
            # report_nm 에는 공백이 잔뜩 붙어 오므로 반드시 정리한다
            "report": " ".join((it.get("report_nm") or "").split()),
            "date": it.get("rcept_dt"),
            # 공시 원문은 이 주소에서 사람이 직접 확인한다
            "url": f"https://dart.fss.or.kr/dsaf001/main.do?rcpNo={it.get('rcept_no')}",
        })

rows.sort(key=lambda r: r["date"], reverse=True)

lines = ["# 수집 로그 — DART 공시", "",
         f"대상: {', '.join(COMPANIES)}", f"기간: {BGN} ~ {END}",
         f"수집: {len(rows)}건", "답하는 질문: Q2  ← 여기를 직접 채우세요", ""]
for r in rows:
    lines.append(f"- [{r['date']}] {r['corp']} | {r['report']} | {r['url']}")

with META.open("a", encoding="utf-8") as f:
    f.write("\n".join(lines) + "\n\n")

print(f"\n총 {len(rows)}건 → {META}")

실제로 돌려 확인한 결과 — 위 4개 회사·6개월 기준 253건 수집. 그중 단일판매ㆍ공급계약체결(수주 공시)이 다수 포함돼 "특별법 전후로 수주가 늘었나" 같은 질문에 바로 활용 가능했음.

5-3-2. fetch_assembly.py — 국회 의안

의안에서 취재적으로 가장 값진 정보는 누가 발의했는가. 발의 의원 명단이 그대로 후반의 개체 대장 '인물' 항목이 됨.

"""열린국회정보 API로 주제 관련 의안과 발의 의원을 받는다."""
import json, os, pathlib, time, urllib.parse, urllib.request
from collections import Counter
from dotenv import load_dotenv

load_dotenv()

# ── 여기만 고쳐 쓰세요 ────────────────────────────────
KEYWORDS = ["해상풍력", "재생에너지", "풍력"]
AGE = "22"                    # 국회 대수
# ────────────────────────────────────────────────────

KEY = os.environ["ASSEMBLY_API_KEY"]
API = "https://open.assembly.go.kr/portal/openapi/nzmimeepazxkubdpn"
OUT = pathlib.Path("2_sources") / "collection_log.md"

# 이 헤더가 없으면 400 Bad Request 가 난다.
# 국회 API는 파이썬 기본 User-Agent(Python-urllib/3.x)를 거부한다.
HEADERS = {"User-Agent": "Mozilla/5.0"}


def bills(keyword):
    """BILL_NAME 부분일치로 의안을 받는다. 페이지를 끝까지 넘긴다."""
    out, page = [], 1
    while True:
        qs = urllib.parse.urlencode({
            "KEY": KEY, "Type": "json", "pIndex": page, "pSize": 100,
            "AGE": AGE, "BILL_NAME": keyword,
        })
        req = urllib.request.Request(f"{API}?{qs}", headers=HEADERS)
        with urllib.request.urlopen(req, timeout=20) as r:
            data = json.loads(r.read().decode("utf-8"))

        root = data.get("nzmimeepazxkubdpn")
        if not root:                      # INFO-200: 데이터 없음
            break
        rows = root[1].get("row", [])
        out.extend(rows)
        if len(rows) < 100:
            break
        page += 1
        time.sleep(0.1)
    return out


seen, all_bills = set(), []
for kw in KEYWORDS:
    got = bills(kw)
    fresh = [b for b in got if b.get("BILL_ID") not in seen]
    for b in fresh:
        seen.add(b.get("BILL_ID"))
    all_bills.extend(fresh)
    print(f"  {kw}: {len(got)}건 (신규 {len(fresh)}건)")

all_bills.sort(key=lambda b: b.get("PROPOSE_DT") or "", reverse=True)

lines = ["# 수집 로그 — 국회 의안", "",
         f"검색어: {' / '.join(KEYWORDS)}  |  {AGE}대 국회",
         f"수집: {len(all_bills)}건 (중복 제거 후)",
         "답하는 질문: Q3  ← 여기를 직접 채우세요", ""]
for b in all_bills:
    lines += [
        f"## {b.get('BILL_NO')}  {b.get('BILL_NAME')}",
        f"- 발의: {b.get('PROPOSER')} | 제안일: {b.get('PROPOSE_DT')}",
        f"- 소관위: {b.get('COMMITTEE') or '[미지정]'} | 처리결과: {b.get('PROC_RESULT') or '[계류중]'}",
        f"- 원문: {b.get('DETAIL_LINK')}", "",
    ]

OUT.parent.mkdir(parents=True, exist_ok=True)
with OUT.open("a", encoding="utf-8") as f:
    f.write("\n".join(lines) + "\n\n")

print(f"\n총 {len(all_bills)}건 → {OUT}")

# 발의 의원은 곧바로 개체 대장의 '인물'이 된다
print("\n대표발의 상위 10명:")
proposers = Counter((b.get("PROPOSER") or "").split("의원")[0]
                    for b in all_bills if b.get("PROPOSER"))
for who, n in proposers.most_common(10):
    print(f"  {who:<12} {n:>3}건")

import pathlib
import pymupdf4llm

SRC = pathlib.Path("2_sources")
OUT = SRC / "sources_md"
OUT.mkdir(parents=True, exist_ok=True)

for pdf in sorted(SRC.glob("*.pdf")):
    md = pymupdf4llm.to_markdown(str(pdf))   # 다단·표 살리고 필요 시 자동 OCR

    target.write_text(md, encoding="utf-8")

    print(pdf.name, "->", target.name, "[", status, "]")

6. 후반 — 확인하기

모은 자료는 아직 문서 더미일 뿐. 여기서부터가 취재임. 개체를 뽑고, 그것을 다른 출처로 확인해 사실 대장을 만듦.

6-0. 왜 추출과 검증을 갈라놓나

이 회차에서 가장 중요한 설계. 개체를 뽑는 일과 확인하는 일을 서로 다른 서브에이전트에 맡김. 각 서브에이전트는 독립된 문맥을 가지므로, 검증자는 추출자가 무엇을 어떻게 판단했는지 모름.

이유 — 같은 문맥 안에서 뽑고 확인하면 모델은 방금 자기가 쓴 내용을 사실로 전제하고 검증함. "A사가 B사업을 수주했다"고 뽑아 놓으면, 이어지는 검증에서 그 문장을 의심하는 대신 뒷받침할 근거를 찾음.

사람 뉴스룸에서 쓴 기자와 확인하는 데스크를 나누는 이유와 정확히 같음. 그래서 verifier에게는 개체와 원문 위치만 넘기고, extractor의 해석·추측은 전달하지 않음.

6-1. 서브에이전트 — .claude/agents/extractor.md

---
name: extractor
description: 2_sources/의 문서에서 인물·기관·기업·금액·날짜·계약 등 개체를 빠짐없이 추출할 때 사용.
tools: Read, Grep, Glob
model: sonnet
---
너는 문서 추출 담당이다. 주어진 문서에서 다음 개체를 뽑는다.
- 인물, 기관/부서, 기업/단체, 금액(단위·기간 명시), 날짜, 계약·사업명, 직위.
- 각 개체가 '어느 문서 몇 페이지'에 나오는지 위치를 반드시 적는다.
  변환본이 아니라 원본 PDF의 쪽수를 적는다.
- 문서에 없는 것은 만들지 않는다. 애매하면 비운다.
- 해석·추측·의미 부여를 하지 않는다. 나온 것을 그대로 옮긴다.
  (검증 담당이 네 판단에 오염되면 안 되기 때문이다.)
결과는 개체별 한 행의 표로 정리해 돌려준다. HTML은 만들지 않는다(메인 세션 몫).

6-2. 서브에이전트 — .claude/agents/verifier.md

---
name: verifier
description: 개체 대장에서 반복 등장·이상 신호 개체를 다른 공개기록과 교차검증할 때 사용.
tools: Read, Grep, Bash, WebSearch, WebFetch
model: opus
---
너는 교차검증 담당이다. 개체 대장에서 여러 문서에 반복 등장하거나
이상 신호(큰 금액, 반복 계약, 시점이 겹치는 거래)가 있는 개체를 골라 확인한다.

- 반드시 "처음 나온 곳과 다른 출처"로 확인한다. 같은 문서로 재확인하는 것은 검증이 아니다.
  예) 공시에서 나온 계약 → 국회 의안·보도자료·뉴스에서 확인
      의안 발의자 → 국회 의안정보시스템 원문에서 확인
- WebSearch로 공식·1차 출처(정부·공시·법원·기관)를 우선 찾고 WebFetch로 확인한다.
- 필요하면 1막의 background-collect 스킬을 재사용해 해당 개체의 언론 등장을 확인한다.
- 확인 결과에 URL과 확인 날짜를 단다. 확인 안 되면 [미확인]으로 남긴다.
- 문서 내용과 공개기록이 상충하면 [상충]으로 표시하고 양쪽을 모두 적는다.
  상충은 오류가 아니라 취재 리드다. 지우지 말고 드러낸다.
- '확인된 사실'만 보고한다. 혐의를 단정하지 않는다.

6-3. 스킬 — .claude/skills/entity-ledger/SKILL.md

---
name: entity-ledger
description: 수집 문서에서 개체를 뽑아 '개체 대장'을 만들 때 사용한다.
---
# 개체 대장(entity ledger) 작성 절차
1. 2_sources/sources_md/ 와 collection_log.md 를 읽는다.
   문서가 많으면 extractor 서브에이전트에 나눠 맡긴다(문서 5~10건씩).
2. 개체를 아래 표에 한 행씩, id를 붙여 정리한다.

| id | 개체 | 유형(인물/기관/기업/금액/날짜/계약) | 값·상세 | 등장 문서·쪽 | 등장 횟수 |
|----|------|------|------|------|------|

3. 같은 개체가 여러 문서에 나오면 한 행으로 합치고 등장 위치를 모두 적는다.
   ★ 서로 다른 소스(공시·의안·뉴스)에 걸쳐 나오는 개체를 특히 주목한다.
     여러 출처에 동시에 등장하는 개체가 취재 가치가 가장 높다.
4. 2회 이상 반복 등장하거나 큰 금액·이상 신호가 있는 개체는 '주목'으로 표시한다.
5. 2_facts/entities.md 로 저장한다.

6-4. 스킬 — .claude/skills/fact-ledger/SKILL.md

이 스킬이 2차 실습 전체의 연결 고리를 만듦. 질문(1막) · 자료(2막 전반) · 검증 결과(2막 후반)를 하나의 표로 묶어, 3막에서 기사 문장이 근거로 삼을 F번호를 부여.

---
name: fact-ledger
description: 검증된 개체와 자료를 질문↔사실↔출처로 묶어 사실 대장을 만들 때 사용한다.
---
# 사실 대장(fact ledger) 작성 절차
입력은 1_plan/reporting_plan.md(질문), 2_facts/entities.md, 2_facts/verified.md 다.
여기 있는 사실만 쓴다.

1. 검증된 사실마다 F1, F2, F3... 번호를 붙여 아래 표로 정리한다.

| id | 사실(한 문장) | 답하는 질문 | 출처(문서·쪽 또는 URL) | 검증 상태 | 확인일 |
|----|------|------|------|------|------|
| F17 | A사가 2026-03-11 B사업 계약을 공시했다 | Q2 | DART 공시 4쪽 (링크) | 확인 | 2026-08-17 |

2. 검증 상태는 셋 중 하나다: [확인] / [미확인] / [상충].
   [미확인]과 [상충]도 반드시 남긴다. 3막에서 쓰지 말아야 할 것을 알려주는 표시다.
3. 질문별로 정리한다. 어느 질문에 사실이 하나도 없으면 그 사실을 명시한다.
   ★ 답을 못 찾은 질문이 3막에서 가장 위험하다. 기사에서 그 부분은 비워 두어야 한다.
4. 근거 없는 관계·추론은 대장에 넣지 않는다. 관계는 같은 문서·같은 계약에
   함께 등장할 때만 적고, 그 근거를 함께 남긴다.
5. 2_facts/fact_ledger.md 로 저장한다. 이 파일이 3막의 입력이다.
6. 사람이 보기 좋은 2_facts/fact_ledger.html 도 함께 만든다
   (CSS 인라인, 상단에 문서 건수·개체 수·사실 수·작성일,
    하단에 "AI가 모은 단서이며 게재 전 사람이 1차 출처로 확인해야 함" 고지).

6-5. 후반 실행

2_sources/의 자료로 개체를 뽑아서 검증해줘. CLAUDE.md 후반 순서대로
개체 대장 → 교차검증 → 사실 대장까지 진행하고, 단계마다 한 줄로 보고해.

단계를 끊어서 지시하면 각 기능이 무엇을 하는지 또렷하게 보임.

extractor 서브에이전트와 entity-ledger 스킬로 개체 대장을 만들어 2_facts/entities.md 로 저장해.
문서가 많으면 나눠서 병렬로 맡겨줘.

verifier 서브에이전트로 여러 소스에 걸쳐 등장하는 개체를 교차검증해서 2_facts/verified.md 로 정리해.
반드시 처음 나온 곳과 다른 출처로 확인해줘.

fact-ledger 스킬로 질문 Q1..Qn 과 검증된 사실을 묶은 사실 대장을 만들어줘.
답을 못 찾은 질문이 있으면 따로 알려줘.

6-6. 빠르게 진행하기 (시간 단축)

2막은 전반·후반 합쳐 40분 가까이 걸림. 후반의 verifier가 15분으로 가장 김(웹 검색 46회). 아래처럼 범위를 정해 주면 절반으로 줄어듦.

전반 — 모으기

자료 수집해줘. 승인 절차 생략하고 아래 범위로 바로 실행해.
- 공개 API만. 웹 직접 수집과 정보공개청구는 목록만 남겨라.
- 뉴스 재수집은 검색어 4개, DEPTH sim 200/date 100, 최근 2년.
- DART는 대상 기업 3개 이내, 기간 1년. 100건 잘리면 반기로만 쪼개라.
- 수집 로그는 파일별 Q 매핑 표 하나로 끝내고 해설은 생략.

후반 — 확인하기

개체 뽑아서 검증해줘.
- extractor는 소스별로 나눠 동시에 띄워라.
- verifier 검증 대상은 5건 이내로 추려라. 고르는 기준은
  ① 기사 리드에 올릴 수치 ② 법령·판결 등 틀리면 오보가 되는 것
  ③ 출처 간 값이 다른 것. 나머지는 [미확인]으로 두고 넘어가라.
- verifier에게: 항목당 WebFetch 5회 상한. 2회 시도해 안 나오면 [미확인].
  법령 조문은 law.go.kr이 프레임 구조라 실패한다.
  법제처 법령해석이나 로펌 뉴스레터로 우회하고 시간 끌지 마라.

줄일 것과 줄이지 말 것

  • DART는 빼도 되는 경우가 많음. 공시 목록에는 보고서명만 오고 계약 상대방·금액·사업명이 없음. 실제 취재에서 1,068건을 받아 기사에 쓴 것은 0건이었음. 기업 자금·계약이 쟁점이 아니면 생략할 것.
  • verifier는 줄이지 말 것. 실제 취재에서 검증 8건 중 4건이 [상충]으로 나옴. 대상을 5건으로 줄이더라도 리드에 올릴 수치 · 법령·판결 · 출처 간 상충 세 기준은 반드시 포함할 것.
  • extractor는 문서를 나눠 동시에 띄우는 것만으로도 크게 단축됨(5개 병렬 시 최장 12분).

7. 3막으로 넘기기 전 점검

3막은 2_facts/fact_ledger.md만 보고 기사를 씀. 대장에 없는 것은 기사에 쓸 수 없음. 그래서 회차를 마치기 전에 네 가지 확인 필요.

  • 모든 사실에 F번호와 출처가 붙어 있는가. 출처 없는 줄은 3막에서 쓸 수 없으므로 지금 삭제.
  • 출처가 원본 위치를 가리키는가. 변환본이 아니라 원본 PDF 쪽수, 또는 확인 가능한 URL이어야 함.
  • [미확인]·[상충]이 남아 있는가. 남아 있어야 정상. 전부 [확인]이라면 검증이 형식적이었을 가능성이 높음.
  • 답을 못 찾은 질문이 무엇인가. 3막에서 기사가 침묵해야 할 지점이자 다음 취재의 출발점.
2_facts/fact_ledger.md 를 읽고 3막 인수인계 점검을 해줘.
출처 없는 사실, 변환본만 가리키는 출처, 답을 못 찾은 질문을 각각 목록으로 보여줘.

8. (선택 심화) 공공데이터포털 붙이기

통계·시설·인허가 현황 같은 자료는 공공데이터포털(data.go.kr)에 있음. 다만 이곳은 다른 API들과 작동 방식이 다름.

키를 발급받아도 바로 쓸 수 없음. 포털의 인증키는 계정 단위로 하나지만, API마다 따로 "활용신청"을 해야 함. 신청하지 않은 API를 호출하면 키가 멀쩡해도 아래처럼 막힘.

HTTP 403
{"errMsg": "SERVICE_KEY_IS_NOT_REGISTERED_ERROR",
 "returnAuthMsg": "등록되지 않은 서비스키", "returnReasonCode": "30"}

키가 잘못된 것으로 오해하기 쉬운 메시지. 이 오류가 나면 키를 다시 만들지 말고 해당 API 페이지에서 활용신청을 눌렀는지부터 확인할 것. 대부분 자동승인이지만 일부는 하루 이상 소요.

사용 순서:

  1. data.go.kr에서 필요한 API를 검색해 활용신청.
  2. 마이페이지에서 승인 확인 후 일반 인증키(Encoding) 복사.
  3. .env에 DATAGOKR_API_KEY=로 저장. 키 끝의 %3D%3D는 URL 인코딩된 ==이므로 그대로 둘 것.
  4. 호출 시 serviceKey 파라미터에 그대로 사용. urlencode()로 한 번 더 감싸면 이중 인코딩이 되어 실패.

시간이 부족하면 이 절은 건너뛰어도 무방. DART·국회·뉴스만으로 2막 실습은 완결됨.

9. 윤리와 법 (반드시)

자동 수집은 편하지만 선을 넘기 쉬움.

  • 공개기록·공개 API만 다루고, 로그인·본인확인이 필요한 자료(판결서 인터넷열람 등)는 자동 수집하지 않음.
  • robots.txt와 사이트 이용약관 준수. 요청 사이에 간격을 둬 서버에 부담을 주지 않음.
  • 저작권 있는 본문은 수집·저장·인용 범위를 지키고, 개인정보는 최소한만 취급.
  • API 이용약관(호출 한도·재배포 조건) 준수.
  • 수집은 취재의 출발일 뿐. 사실 확인과 게재 판단·책임은 사람 기자에게 있음.

후반의 검증에는 별도의 위험이 있음.

  • AI가 뽑은 개체·관계는 모두 '단서'. 게재 전 사람이 원문과 1차 출처로 반드시 확인.
  • 개체와 관계에 환각(없는 인물, 없는 연결)이 생길 수 있음. 근거 문서가 없는 관계는 버릴 것.
  • 같은 이름이 다른 사람·다른 법인일 수 있음. 동명이인·유사 상호를 특히 주의.
  • 공개기록만 다루고 미확인 혐의를 단정하지 않음. 명예훼손·프라이버시 위험이 있으면 즉시 중단.

10. 3시간 진행 순서

전반 90분, 후반 90분입니다. 중간에 쉬는 시간을 둡니다.

전반 — 모으기

  • 0부(10분): 왜 API 우선인가 — 수집의 3단(API → 브라우저 → 스크랩)과 법·윤리. 1막의 질문 목록 다시 보기.
  • 1부(20분): 세팅 — .venv 활성화, pip install pymupdf pymupdf4llm, .env에 DART·국회 키 추가, CLAUDE.md에 2막 순서 덧붙이기, Playwright MCP 연결.
  • 2부(35분): API 수집 — fetch_dart.py로 대상 기업 공시, fetch_assembly.py로 관련 의안·발의 의원.
  • 3부(20분): 브라우저 수집 — Playwright MCP로 부처 보도자료 받기. (여유가 있으면 Scrapling 시연)
  • 4부(5분): PDF 변환과 수집 로그 점검 — 어느 Q에 답하는 자료인지 다 적혔는지.

후반 — 확인하기

  • 5부(10분): 왜 추출과 검증을 갈라놓나 — 쓴 기자와 확인하는 데스크의 분리.
  • 6부(30분): 개체 추출 — extractor를 문서 묶음별로 나눠 병렬 실행, 개체 대장 작성.
  • 7부(30분): 교차검증 — 여러 소스에 걸쳐 등장하는 개체를 다른 출처와 대조. [상충]을 찾아내기.
  • 8부(15분): 사실 대장 — 질문↔사실↔출처를 F번호로 묶기.
  • 9부(5분): 3막 인수인계 점검 — 답을 못 찾은 질문 확인.

강사 메모: 7부가 이 회차의 승부처입니다. 수강생이 가장 놀라는 지점은 [상충]이 나올 때입니다. 공시의 계약 금액과 보도자료의 사업비가 안 맞거나, 의안 제안 시점과 기사 시점이 어긋나는 경우를 하나만 찾아내도 "AI가 취재를 대신하는 게 아니라, 사람이 볼 곳을 좁혀 준다"는 메시지가 몸으로 전달됩니다. 미리 [상충] 사례를 하나 준비해 두면 좋습니다.

6부의 병렬 추출은 문서가 20건 이상일 때 체감됩니다. 수집이 적게 된 조는 강사가 준비한 2_sources.zip을 풀어 쓰게 하세요.

Codex로 만들기

이 실습은 Claude Code 기준이지만 OpenAI Codex로도 그대로 진행 가능. 개념이 1:1로 대응되고 파일 이름·형식과 실행 명령만 다름. 이 회차는 서브에이전트 3개와 MCP를 쓰므로 1막보다 변환할 것이 조금 많음.

개념 Claude Code OpenAI Codex
프로젝트 지침 CLAUDE.md AGENTS.md (내용 동일)
스킬 .claude/skills/<이름>/SKILL.md SKILL.md (자동 로드, 호출은 $이름)
서브에이전트 .claude/agents/<이름>.md .codex/agents/<이름>.toml
MCP 연결 .mcp.json ~/.codex/config.toml 의 [mcp_servers]
실행 claude codex
계획·검토 Shift+Tab 플랜 · /review /plan · /review
권한 승인 프롬프트 샌드박스(read-only / workspace-write / danger-full-access)

바꿀 것은 다음뿐입니다.

  1. CLAUDE.md를 AGENTS.md로 이름만 바꿉니다(내용 그대로).

  2. 서브에이전트 세 개(collector·extractor·verifier)를 .codex/agents/<이름>.toml 로 옮깁니다. 마크다운 프론트매터 대신 TOML 키(name·description·developer_instructions)를 씁니다. 검증자를 별도 에이전트로 두는 구조는 Codex에서도 그대로 유지해야 합니다.

# .codex/agents/collector.toml
name = "collector"
description = "..."            # 기존 description 그대로
developer_instructions = """
... 기존 지침 본문 그대로 ...
